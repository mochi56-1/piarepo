# ログインボーナス

## 今回の範囲

- 日本時間で1日1回、受け取りボタンで10コイン。
- 累計をホーム・マイページの両方で表示。
- noteや反応の有無は条件にしない。連続ログインのリセット・減点はない。
- コインの交換所・着せ替え・note等のクラウド移行は今回の範囲外。
- Supabase未接続なら「お試し」と明示して、別キーにブラウザ内保存。本番のコインへ自動移行しない。

## Supabase作成後の設定

本番利用には、以下のSupabase・Vercel設定が必要です。コードの公開だけでは接続確認は完了しません。

1. Supabaseで新しいプロジェクトを作成。データベースのパスワードや管理者用キーはチャットやコードに貼らない。
2. SupabaseのSQL Editorで [初期SQL](../supabase/migrations/202610220001_login_bonus.sql) を実行。新しいプロジェクト向け。再実行しても既存コインは削除しない。
3. Authのメール認証を有効にする。メール内のログインリンクを使う方式。
4. 認証のURL設定でSite URLをぴあれぽの本番公開URLにする。Redirect URLsにも同じ公開URLを登録。ローカル検証する場合だけ `http://localhost:5173` を追加。プレビューURLを使う場合も必要なものだけ追加する。
5. プロジェクトURLと**公開用 publishable key**を確認。旧anon keyも対応。`service_role` や `sb_secret_` のキーを使わない。
6. 手元では `.env.example` を参考に `.env.local` を作り、`VITE_SUPABASE_URL` と `VITE_SUPABASE_PUBLISHABLE_KEY` を設定して開発サーバーを再起動する。`.env.local` はGit管理しない。
7. ボーナス版のコードを公開する際は、VercelのProduction環境変数にも同じ2項目を設定し、ビルドし直す。Viteはビルド時に公開設定を読み込む。
8. ログインメールのリンクを、利用したい同じブラウザで開く。受け取り・累計・別端末での同日受け取り済みを実機で確認。

環境変数の値はフロントエンドに含まれます。管理者キーを設定した場合はビルドを失敗させて、公開を止めます。公開キー自体で認可するのではなく、RLSとサーバー関数が本人だけの操作に限定します。

Supabase標準メールの制限や配信設定によりメールが届かない場合は、認証サービス側のログ・配信設定を確認してください。

## 二重付与を防ぐ仕組み

- `login_rewards` は `user_id + reward_date` が主キー。日付・10コインはサーバーが決定し、クライアントの時刻や希望額は受け取らない。
- `claim_login_bonus()` はログインユーザーIDを `auth.uid()` から取得し、衝突時は追加しない。再試行・別端末からの同日受け取りでも行を増やせない。
- 残高は本人の受け取り履歴の合計。クライアントによるテーブルへの挿入・更新・削除は許可しない。行の参照も本人だけ。
- 未ログインではRPC実行不可。関数は固定の空search_pathと完全修飾名で定義。
- アカウント切り替え時は前の残高を消し、遅れて返った別アカウントの結果は表示しない。
- お試しの保存キーは `piarepo-login-bonus-demo-v1`。端末の時刻に依存するデモで、複数端末間の共有や改ざん対策を提供しない。

## 既存データとの関係

この文書はボーナス初期導入の説明です。新しいアカウント保存対応版は [追加導入手順](accounts-and-friends.md) のSQLが必要です。設定後はnote・写真・タスク・予定もアカウント別に保存します。以前のブラウザ記録は確認して取り込みます。

コイン履歴はSupabaseが保存し、noteのJSONバックアップには含めません。お試しコインもnoteバックアップの対象外です。

## 検証

- `npm test`：既存7件に加え、日本時間の0時、同日の繰り返し受け取り、間が空いた場合、保存失敗、破損・重複データの計5件。
- SQL用の3件も `npm test` に含みます。
- PostgreSQL互換エンジンPGliteで実際の初期SQLを実行。1アカウント1日1行、本人以外のRLS、クライアントの直接書き込み拒否、匿名RPC拒否、反復付与、日付境界を確認。実Supabaseや複数DB接続での同時実行を確認したとは扱わない。
- ブラウザでは、お試しの受け取り・再読込・マイページとの累計一致・翌日・容量不足を確認。
- 接続済みモードも模擬サービスで確認：メールリンク要求、認証済みRPC、別アカウントの残高が残らないこと、ログアウト。実際のメールやSupabaseリクエストは送信していない。
- ビルド設定で新形式の管理者キー・旧service-roleキーの公開を拒否することを確認。
- 本番Supabaseへの接続・メールの実配信・実機iPhoneでのログインは未確認。設定した本番環境での確認が必要。

## Googleログインの追加設定

1. Google Cloud Consoleでプロジェクトを選択し、Google Auth Platformでアプリ名・サポートメール・連絡先を設定する。
2. 一般のGoogleアカウントを対象にする場合、AudienceはExternalを選ぶ。Testing中はログインするGoogleアカウントをTest usersへ追加する。一般公開前には公開状態・Google側の要件を確認する。
3. SupabaseのAuthentication → Sign In / Providers → Googleを開く。表示されたCallback URLをコピーする。
4. Google側でOAuthクライアント（種類：Web application）を作成し、Authorized redirect URIsへ上記Callback URLをそのまま登録する。VercelのURLではなくSupabaseのコールバックを指定する。
5. 発行されたClient IDとClient SecretをSupabaseのGoogleプロバイダー設定に入れ、有効化して保存する。Client Secretはチャット・Git・VercelのVITE変数に入れない。
6. SupabaseのSite URL・Redirect URLsに、利用するぴあれぽの公開URLを登録する（メールログインと共通）。
7. Googleログイン対応版をデプロイ後、「Googleでログイン」から認証し、アプリへ戻ることとコインの受け取りを確認する。実機iPhoneでもSafariから確認する。

アカウント保存対応版の導入前は、Googleログインでも同期対象はコインのみ。メールログインとのアカウント統合はSupabaseの認証設定・メール検証状態に依存するため、既存ユーザーは同じメールアドレスを使い、受け取り前に累計を確認する。
Googleプロバイダー未設定ではボタンからログインできない。コード追加だけでGoogle側の設定が完了したとは扱わない。
